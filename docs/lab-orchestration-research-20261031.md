# 연구실 칼럼이 구조적으로 통과하는 오케스트레이션 — 조사와 제안

작성 2026-10-31. B안 파일럿 2회(`logs/lab-upgrade-eval/b-pipeline-trial`, `-v2`)의 단계 기록과 외부 연구·오픈소스를 대조해, 보류가 기본값이 되는 원인과 구조적인 해결책을 정리했어요. 같은 날 독립 검증 모델은 Astra high에서 Sol high로 바꿨어요(`office/model_router.py`).

## 1. 결론

지금 파이프라인은 **"쓰고 나서 웹으로 다시 확인하고, 틀리면 다시 쓰는"** 구조예요. 연구 결과와 파일럿 기록은 이 구조가 비싸고 수렴하지 않는다는 점에서 일치해요. 바꿀 방향은 세 가지예요.

1. **근거 원장을 먼저 만들고, 원장 안에서만 쓰기.** 웹은 수집 때 한 번만 열고, 원문 발췌를 저장해요. 검증은 웹 재탐색이 아니라 저장된 발췌와 문장을 대조하는 일이 돼요.
2. **사실 관문과 편집 관문을 분리.** 사실은 통과/실패의 이진 관문으로, 기계 점검과 원장 대조로 판정해요. 문장·구성 품질은 점수로 따로 보고, 사실을 새로 들이지 못하는 한 번의 편집으로 처리해요.
3. **주제 유형별 구조.** 코딩 튜토리얼에 데이터 저널리즘 틀을 강제하지 않아요.

## 2. 파일럿에서 확인한 근본 원인

두 파일럿의 팩트체크·재검증에서 걸린 주장은 28건이에요. 한 주장이 여러 유형에 걸릴 수 있어요.

| 유형 | 건수 | 예 | 해결 방향 |
|---|---:|---|---|
| 코드·테스트 동작 | 12 | assertNumQueries가 감싸는 범위, 클래스 밖 테스트 메서드, 예상 쿼리 수 | 실행 검증(구현됨) |
| 단정 표현 | 9 | "항상 객체 하나", "반드시 쿼리 1회", "가장 빠른 방법" | 기계 점검으로 집필 직후 차단 |
| 남의 글·현장에 대한 일반화 | 7 | "흔한 소개글은 …에서 끝납니다", "팀 코드에서 실제로" | 구조 개편(아래 원인 B) |
| 버전 번호 오판 | 3 | "LTS인 5.2" | 수정됨 |

**원인 A — 원장 밖에서 쓰는 집필.** v2의 설계도는 주장 14개를 확인했는데(7개 확인·7개 확인 불가, 확인 불가는 주로 대상·기간 범위 불일치), 초안의 첫 팩트체크에서 다시 8건이 틀렸어요. 작가가 확인된 범위를 넘어서 새 주장을 계속 만들어요.

**원인 B — 장르에 맞지 않는 고정 틀.** `REQUIRED_SECTIONS`(왜 지금인가 / 숫자로 보는 현황 / 현장의 변화)가 모든 주제에 강제돼요. 코딩 튜토리얼은 이 칸을 채우려고 해명 문장("이 글은 보급률 통계 대신…")과 일반화("현장 적용 사례")를 써요. 편집장 필수 수정은 v1에서 6건 중 3건, v2에서 6건 중 2건이 이 틀 때문이었어요. 평론 4회는 모두 같은 점을 지적했어요.

**원인 C — 수정이 새 결함을 만듦.** 조정 전 B안은 9,016자에서 11,954자로 늘면서 새로 틀린 테스트 주장 3건이 생겼어요. v2는 패치 29건 뒤 새 오류 1건이 생겼어요. 패치 범위가 필수 수정 위치로 제한되지 않고, 새 사실 문장을 막는 장치가 없어요.

**원인 D — 변경분 검증이 실제로는 작동하지 않음.** `delta_review.scope_check`는 직전 검증이 `pass`일 때만 작동해요. 재검증이 필요한 경우는 직전 검증이 `revise`일 때이므로, 필요한 순간에는 늘 전체 재검증(웹 재탐색)으로 가요. 코드 블록이 조금만 바뀌어도 전체로 넘어가요. 원장에 남는 근거(`pack_text`)도 300자 한 문장이라, 웹 없이 대조하기에는 짧아요.

**원인 E — 한 심사에 사실·문장·구성이 섞임.** 편집장 필수 수정에 사실 결함과 문장·구성 지적이 함께 들어가요. 그래서 필수 수정이 늘 6~7건이 되고, 수정 1회 제한 안에서는 보류가 기본값이 돼요.

**원인 F — 차별점 결정이 늦음.** 평론가가 "상위 글과 같은 틀"이라고 지적한 시점은 원고가 완성된 뒤예요. 경쟁 글 조사가 기획이 아니라 평론 단계에 있어요.

## 3. 외부 근거

| 근거 | 핵심 | 이 파이프라인에 주는 의미 |
|---|---|---|
| Huang et al., *LLMs Cannot Self-Correct Reasoning Yet* (ICLR 2024) | 외부 피드백 없는 자기 수정은 성능이 정체하거나 떨어지고, 맞는 답을 틀리게 바꾸기도 해요. 코드 실행 결과·검색 같은 외부 신호가 있을 때 수정이 효과적이에요. | 수정 루프는 의견이 아니라 외부 신호(실행 결과, 원문 발췌, 기계 점검)로 돌려야 해요. 원인 C의 근거예요. |
| RARR (Gao et al., ACL 2023) | 생성 뒤 근거를 찾아 지지되지 않는 부분만 고치고, 원문 보존을 함께 측정해요. 귀속만 최적화하면 원문을 통째로 바꾸는 편집이 높은 점수를 받을 수 있다고 경고해요. | 패치는 "근거 귀속 + 보존"을 함께 봐야 해요. 고친 범위 밖의 변경을 막는 장치가 필요해요. |
| ALCE (Gao et al., EMNLP 2023) | 검색한 구절에 인용을 붙여 쓰게 하고, 인용 품질을 자동 평가해요. 최고 모델도 약 절반은 인용 지지가 완전하지 않았어요. | 문장마다 근거 ID를 달게 하고, 그 ID로 대조해요. 근거 없는 사실 문장은 기계로 찾을 수 있어요. |
| MiniCheck (Tang et al., EMNLP 2024) | 근거 문서에 대한 사실 대조는 작은 모델로도 GPT-4 수준에 가깝게, 400배 낮은 비용으로 할 수 있어요. 주장 분해가 늘 도움이 되지는 않았어요. | 검증의 대부분은 웹 탐색이 아니라 "문장 ↔ 저장된 발췌" 대조예요. 웹 없이, 짧은 입력으로 할 수 있어요. |
| SAFE (Wei et al., NeurIPS 2024) | 응답을 개별 사실로 나눠 사실마다 검색으로 확인해요. 사람 평가와 72% 일치, 약 20배 저렴. | 웹 검증은 새로 등장한 주장에만 써요. |
| Chain-of-Verification (Dhuliawala et al., 2023) | 검증 질문을 원래 답을 보지 않고(factored) 따로 답하면, 원래 환각을 반복하지 않아 정확도가 올라가요. | 검증관에게 원고 전체 대신 "주장 + 발췌"만 줘요. 토큰도 줄어요. |
| STORM (Stanford OVAL) | 쓰기 전에 다관점 질문으로 자료를 모아 개요를 만들고 나서 써요. | 차별점과 독자 질문은 기획 단계에서 정해요(원인 F). |
| Anthropic, *Building effective agents* | 평가자-최적화자 루프는 평가 기준이 명확하고 반복이 측정 가능한 개선을 줄 때만 적합해요. 가장 단순한 구조부터 써요. | 문장·구성처럼 기준이 흐린 심사는 반복 루프 대신 한 번의 편집으로 둬요. |
| LLM 심사 편향 정리(MT-Bench 보고 등) | 점수형 심사는 실행마다 흔들리고, 기준점이 있는 척도가 변동을 줄여요. 같은 계열 모델은 자기 글을 선호하는 경향이 있어요. | 발행 여부를 점수 하나에 걸지 않아요. 사실은 이진 관문, 품질은 기준 칼럼과 비교해요. |
| Loki / OpenFactVerification (COLING 2025 Demo) | 분해 → 확인 가치 판정 → 질의 생성 → 근거 검색 → 판정의 5단계. 사람 판단을 돕는 도구로 설계됐어요. | 모든 문장이 아니라 "확인 가치가 있는 주장"만 검증해요. |
| LangChain open_deep_research | 감독자가 연구 과제를 나누고, 연구자가 독립 맥락에서 조사한 뒤 결과를 압축해 넘겨요. | 조사 결과는 원문 전체가 아니라 압축된 발췌로 넘겨요. 토큰 절감의 핵심이에요. |
| 언론사 AI 정책(AP 기준 인용 정책 등) | AI 결과물은 검증 전 자료로 취급하고, 발행 전 사람 검토를 기본으로 해요. | 자동 발행에는 사실 관문 통과를 필수로 하고, 사람 검토 비용을 줄이는 검수 묶음을 만들어요. |

## 4. 제안 — 근거 원장 우선 파이프라인

```text
기획(+경쟁 글 차이 1줄, 장르 선택)
 → 근거 수집 [Sol medium, 웹 1회] → 원장: 주장·출처·발췌(문단 단위)·해시 / 코드 실행 결과
 → 개요(섹션마다 사용할 주장 ID)            [Opus]
 → 집필(사실 문장마다 숨은 주장 ID)          [Opus]
 → 기계 관문(토큰 0): 주장 ID 해석, 수치 잠금, 단정·일반화 점검, 코드 정적·실행, 장르 섹션, 분량
 → 사실 관문 [Sol high, 웹 없음]: 문장 ↔ 원장 발췌 대조(원고 전체를 보지 않음). 원장에 없는 주장만 웹 확인
 → 편집 관문 [Opus 편집장 + 평론가]: 구성·명료성·약속한 차별점. 결과는 문장 ID 단위 편집안
 → 편집 1회(사실 문장 잠금, 새 사실 문장 금지) → 기계 관문 → 바뀐 문장만 사실 관문
 → 발행 판단
```

### 4.1 단계별 변경

| 단계 | 지금 | 제안 | 해결하는 원인 |
|---|---|---|---|
| 기획 | 각도·필요 지표 | + 장르(튜토리얼/해설/데이터), + 상위 글과의 차이 1줄(웹 1회) | B, F |
| 근거 수집 | 주장 확인, 발췌 300자 | 발췌를 문단 단위로 저장(원문 해시와 함께). 코드 실행 결과도 원장 항목으로 | D |
| 집필 | 원장을 참고 자료로 줌 | 사실 문장에 숨은 주장 ID(`<!--c:ID-->`) 필수. ID 없는 문장은 절차·의견만 | A |
| 기계 관문 | 분량·섹션·문체·수치 | + 단정 표현(항상·반드시·가장·모든·유일), 일반화(흔한·대부분의 글·현장에서), ID 없는 사실 문장 | A, C |
| 사실 검증 | 웹 도구로 원고 전체 재검증 | 원장 발췌 대조(웹 없음). 문장·주장·발췌만 입력. 원장에 없는 주장만 웹 | D, 비용 |
| 편집 심사 | 점수 + 필수 수정(사실 포함) | 사실 결함은 사실 관문 몫. 편집장은 구성·명료성·차별점만, 문장 ID 단위 편집안 | E |
| 수정 | 패치 29건, 범위 제한 없음 | 사실 문장 잠금, 편집안 위치만 변경, 새 사실 문장이 생기면 거절 | C |
| 재검증 | 직전 `pass`일 때만 변경분 | 직전 판정과 무관하게 바뀐 문장만 원장 대조 | D |

### 4.2 장르별 구조(제안)

- **튜토리얼·해설(코딩):** 리드(막히는 장면) → 판단 기준 → 동작 원리 → 실행 예제(실행 확인된 출력·쿼리 수) → 함정 → 체크리스트 → 참고 자료.
- **데이터(통계 주제):** 지금의 구조를 유지해요(왜 지금인가 / 숫자로 보는 현황 / 현장의 변화 / 시사점).
- 장르는 기획에서 정하고, `precheck_draft`의 필수 섹션은 장르에 따라 골라요.

### 4.3 발행 방법

| 관문 결과 | 처리 |
|---|---|
| 기계·사실 관문 통과 + 편집 기준 이상 | 예약 공개(지금처럼). 점수는 프리미엄·노출 판단에만 사용 |
| 기계·사실 관문 통과 + 편집 기준 미달 | 편집 1회 후 재심. 여전히 미달이면 운영자 검수. 사실이 맞는 글이므로 검수는 문장 품질 판단만 |
| 사실 관문 실패 | 보류. 운영자 검수 묶음에 "틀린 주장 ↔ 원장 발췌", 실행 결과, 변경 비교를 넣어 1~2분 안에 판단하게 |

- 공개 뒤 정정 기록(무엇을 언제 고쳤는지)을 남겨요. 언론사 AI 정책들도 사람 검토를 기본으로 하는데, 이 사이트의 운영자 검수 권한은 지금처럼 유지해요.
- **예산 장치:** 실행당 Codex 입력 토큰 상한을 둬요. 첫 사실 관문에서 틀린 주장이 많으면(예: 6건 이상) 수정하지 않고 바로 보류해요. 그러면 보류되는 글이 한도를 다 쓰지 않아요.

### 4.4 예상 비용 (추정 — 파일럿으로 확인해야 해요)

v2 기준 Codex 입력은 약 118만 토큰이었어요. 근거 수집 71만, 팩트체크 22만, 재검증 11만, 기획·설계 보조 12만이에요.
- 팩트체크와 재검증이 웹 없는 원장 대조로 바뀌면, 입력은 "주장 + 발췌"만큼만 들어요. 주장 15개 × 발췌 1,500자로 잡으면 수만 토큰 규모예요. 33만 토큰 중 대부분이 줄 것으로 보여요.
- 근거 수집은 주장 수 상한(지금 16개)과 수집 대상(확인 가치가 있는 주장만)으로 줄여요. 효과는 측정 전에는 말할 수 없어요.
- 위 숫자는 추정이에요. Sol medium과 Sol high가 같은 토큰에 한도를 얼마나 차감하는지도 확인하지 못했어요.

## 5. 구현 순서

| 순서 | 내용 | 토큰 비용 | 확인 방법 |
|---|---|---|---|
