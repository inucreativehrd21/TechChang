# 칼럼 제작 예산 중단과 빈 원고 복구

## 2026-11-13 운영 관측

운영 소스 `be235c8b9356ef0404b2eabb9c7e7cecc84efc8e`, 프로필 A에서 코딩 심화 원고 #59와 실용 원고 #60이 각각 호출 24회에서 멈췄어요. 소요 시간은 1,179.89초와 1,167.4초로 2,400초 시간 상한에 도달하지 않았어요. 구독 제공자 한도가 아니라 `RunContext`의 호출 상한이에요.

두 실행 모두 기획 2회·설계도/근거 사전 검증 6회를 사용했어요. 이후 팩트체크 보완, 편집 보완, 기준선 부근 3회 심사까지 같은 24회 예산을 썼어요. 예약 제작은 두 번째 자동 보완도 시도하므로 마지막 재심 또는 재검증 직전에 중단될 수 있었어요.

더 큰 복구 장애는 `ColumnDraft` 제목·본문·보고서를 제작 완료 때만 저장한 것이었어요. 중단된 원고는 `hold`이지만 본문은 비어 있었고, 메일에서 재심을 요청할 수 있었어요. 운영 작업 #15·#16은 프로세스상 `completed`였지만, 수정 결과는 원고를 유지하는 `retained`였어요. 실제로 수정 가능한 본문이 없었어요.

운영 로그·DB는 읽기 전용으로 조사했어요. 이 문서와 함께 준비한 변경은 아직 배포하지 않았고, 원고 복구·추가 재심·공개도 실행하지 않았어요.

## 변경한 처리

- 초고가 나오면 빈 원고에 제목·본문을 저장해요. 체크포인트 재개 시 이미 저장된 검수본을 초고로 덮어쓰지 않아요.
- 편집 심사마다 동일 버전의 제목·본문·팩트체크·심사·도판 정보를 함께 저장해요. 보완 도중 예외가 나면 직전 검수본으로 재심할 수 있어요.
- 추가 자동 보완은 기본 9회(도판 생략 시 8회)·600초 이상이 남았을 때만 시작해요. 패치, 전체 재작성 대체 경로, 팩트체크, 도판, 평론, 3회 심사를 고려한 착수 기준이에요. JSON 재시도·추가 중재까지 보장하는 예약은 아니며, 실제 24회·2,400초·Codex 입력 상한은 계속 적용해요.
- 예산이 부족하면 현재 심사 결과로 보류하고 필수 수정을 남겨요. 미검증 수정본을 통과 처리하거나 예산을 초기화하지 않아요.
- 실제 상한 중단은 호출 수/시간/토큰 원인을 구분해 기록해요. 패치 호출의 예산·제공자·실행 권한 중단은 전체 재작성으로 우회하지 않아요.
- 빈 원고의 재심은 모델 호출 전에 차단하고, 메일에도 사용할 수 없는 재심 버튼을 붙이지 않아요.

## 기존 빈 원고 복구

`office_recover_draft`는 기본적으로 후보만 확인해요. `StageRun`에서 심사 본문 전체 SHA-256, 제목, 팩트체크 본문 지문이 일치하는 마지막 **복구 가능한** 검수본을 찾아요. 더 최신 수정본이 있어도 정확한 대응을 입증하지 못하면 사용하지 않아요. 제작 기록을 합성해 새 본문이나 심사 통과를 만들지 않아요.

운영 기록에 새 탐색 코드를 임시로 읽기 전용 실행하여 아래 후보를 확인했어요. 코드 파일은 운영에 저장하지 않았어요.

| 원고 | 복구 후보 | 점수 | 본문/팩트체크/심사 StageRun ID | 본문 SHA-256 |
|---|---|---:|---|---|
| #59 | 0.1 + 0.2가 0.3이 아닌 이유, 부동소수점 저장과 반올림 | 73 | 584 / 585 / 588 | `9a77f56c893c794fd09fc43ab7e4b00bc0e564e42481f22a350c6dc69f2845d8` |
| #60 | 로컬 AI 뜻과 클라우드 차이, 세 질문 판단법 | 70 | 606 / 607 / 610 | `097e43ca7413c36f54bfcfaa27920192897930657dfc91461e504909e531fd81` |

운영 반영을 요청받은 뒤 최신 작업 상태를 다시 확인하고 실행해요. 아래 명령의 `python`은 운영 가상환경 실행 파일을 뜻하며, Windows에서는 `py -3.10`을 사용해요.

```sh
python manage.py office_recover_draft --draft 59
python manage.py office_recover_draft --draft 60
# 위 후보를 확인한 뒤에만 DB 복구를 적용해요.
python manage.py office_recover_draft --draft 59 --apply
python manage.py office_recover_draft --draft 60 --apply
```

복구는 본문이 비어 있는 보류·실패 원고만 허용해요. 해당 원고의 대기·실행·격리 작업이 있으면 거절해요. 행 잠금 안에서 기존 빈 원고의 보고서와 출처를 감사 기록에 보존하고, 본문·보고서를 복구해요. `human_approval`과 `evidence_run_id`는 가져오지 않아요. 상태는 보류이며 새 검증·심사·승인이 필요해요. 기존 제작 이력과 운영자 수정 지시는 지우지 않아요.

예산을 모두 쓴 `--resume-run`은 예산을 새로 주지 않아요. 소스 지문이 바뀐 배포 뒤에는 과거 체크포인트 재개도 거절돼요. 이 두 원고는 제작 처음부터 재실행하는 대신 위 검수본 복구 후 기존 관리자 재심 흐름으로 이어가요.
