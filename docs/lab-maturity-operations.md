# 연구실 고도화 운영 인계

> 최초 구현의 운영 이력이에요. [현행 운영 문서](lab-operator-hardening.md)의 승인 정책·독립 감시·실행 신원·마이그레이션 목록을 우선해요.

기본 정책은 A 제작 → 검수 대기 → 운영자 승인 → 예약 공개예요. B는 비교 실증 뒤 선택해요.
승인은 제목·본문과 검증·심사 근거 및 운영자에 묶여요. 수정하면 다시 승인해야 해요. 오래된 검증·사실 실패는 예외 사유로도 공개할 수 없어요. 명시적인 형식 결함만 사유를 남겨 예외 승인할 수 있어요.

## 배포 시 적용 순서

1. 진행 중인 연구실 작업이 없는지 확인하고 DB를 백업해요.
2. 사용자 배포 요청이 있을 때 `0015_job_lifecycle`, `0016_human_review`를 적용해요.
3. 기존 10분 `office_release` cron은 공개 전용으로 유지해요.
4. 같은 사용자·프로젝트·가상환경으로 `* * * * * ... manage.py office_work_jobs >> .../logs/office-worker.log 2>&1`를 추가해요. 중복 실행은 파일 잠금으로 거절해요.
5. 로컬 가짜 작업으로 대기·완료를 확인한 뒤, 운영에서 관리자 작업 한 건의 상태와 웹 재시작 후 생존을 확인해요. 이 확인 전에는 운영 격리 완료로 보고하지 않아요.

실행기는 한 번에 하나씩 처리하므로 1분 내 시작은 유휴 상태 기준이에요. 실행 제한은 45분이에요. 실행 중 중단한 작업은 자동 반복하지 않고 확인 후 재개해요. 프로세스 시작 실패만 한 번 재시도해요. PID가 살아 있으면 중복 실행을 피하려고 기다리므로 PID 재사용이 의심되면 프로세스 명령행을 직접 확인해요.

되돌릴 때는 새 작업 등록을 멈추고 실행기 cron을 중지한 뒤 실행 중 프로세스 종료를 확인해요. DB 필드는 제거하지 않아요. 이미 승인·공개한 글은 유지해요. 이전 코드로 돌아가면 자동 공개 정책도 달라지므로 공개 cron은 재검토 전 중지해요.

## 품질 측정과 실증

`lab_quality_report --days 30 --output logs/lab-quality.json`은 심사 전 실패도 포함해요. 과거 누락 사용량은 미측정이고 사람 평가는 별도예요. Django 관리자 HumanReview에서 실행 UUID, 효용(1~5), 사실 오류·심각도, 승인 여부, 검수 시간과 공개 후 정정을 기록해요.

`lab_pilot --output logs/lab-maturity-pilot`은 3주제·6편 목록만 만들어요. 로컬 DEBUG 설정에서 `--execute`를 붙이면 임시 테스트 DB에서 실제 구독을 순차 사용해요. 운영 데이터는 평가 대상으로 쓰지 않아요. 원고·단계·실패 기록과 blind 폴더를 남기고 테스트 DB는 제거해요. blind 폴더만 평가자에게 전달하고 프로필 대응표는 분리해요. 빈 원고·중단도 실패 표본으로 포함해요.

B 기본 전환은 세 B 원고 모두 사람 승인, 중대한 사실 오류 0, A 이상 효용, 검수 시간 중앙값 20% 이상 감소를 모두 만족할 때만 검토해요. 6편은 무인 발행 안전성의 증거가 아니에요. 추가 실행은 실패 원인과 남은 구독 예산을 확인한 뒤 결정해요.
