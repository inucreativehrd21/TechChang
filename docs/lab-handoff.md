### 2026-11-23 판별 지적 장부·판 비교·제목 점검·토큰 탭 (로컬 구현, 운영 미배포)

재작성이 직전 판만 보고 초안의 좋은 대목을 잃거나 해결한 지적을 되돌리던 문제를 고쳤어요. 사람 평가로 품질 향상을 확인한 것은 아니에요.

- **지적 장부** `office.revision_ledger` + `RevisionLedger`(mig office `0023`): 원고 저장 신호로 판마다 지적을 이어 붙여요. 해결은 근거(수정 검증 인용·편집장 해결 판정·팩트체크 통과·주장 삭제)가 있을 때만 잠그고, 근거 문장이 사라지면 회귀로 되돌려요. 승인 지문(`audit.snapshot`)에는 포함하지 않아요.
- **원고 카드**: 판별 점수 흐름, 지적마다 새·반복·회귀·해결 표시. 기본 선택은 필수 수정·팩트체크·회귀·사라진 강점이고 제안은 해제예요. 해결된 지적은 '다시 열기'를 체크해야만 보내며 서버도 막아요(감사 기록 `reopened`). 새 id `G`(회귀)·`K`(사라진 강점)는 `security.validate_args`가 허용해요.
- **지켜야 할 강점**: 편집장 `keep` + 평론가 `strengths` 중 본문에 실제로 있는 인용(`qa.keep_passages`). 재작성 지시에 `preserve_passages`·`already_resolved`로 넘기고, 요청과 무관하게 사라지면 코드가 보완본 채택을 막아요(`lost_passages`).
- **판 나란히 비교** `office.pairwise`(스위치 `pairwise_guard`, 기본 켜짐): 관리자 재작성 채택 전, 자동 재작성 뒤 마지막 판이 앞선 판보다 낮을 때 순서를 바꿔 두 번 비교해요. 두 번 모두 앞선 판이 나을 때만 지키고, 엇갈리면 기존 점수 규칙을 따라요. 앞선 판은 그 판 그대로 사실 검증을 통과했어야 해요.
- **제목 점검** `office.headline`(스위치 `title_lab`, 기본 켜짐): 100점 심사와 별도로 점검표 5문항 + 길이·단정·중복 검사, 검색형·은유형·질문형 후보 3개. 제목은 자동으로 바꾸지 않고 카드에서 고르면 제목 요구가 담긴 재작성 요청이 돼요. 제목 다듬기 지시문에서 "검색어, 설명" 공식을 막았어요. `title_ctr_report`로 제목 결별 GSC 클릭률·평균 순위를 비교해요.
- **토큰 탭** `/lab/admin/tokens/`(`office.token_usage`): 칼럼별·단계 묶음별 입력·출력, 팩트체크 호출·웹·도구 턴·1,000자당 토큰·중앙값 대비, 누수 신호(도구 결과로 불어난 호출·같은 본문 재검증·호출 과다·중앙값 2배·측정 누락), 채택 안 된 재작성 토큰. 이를 위해 호출 기록에 `prompt_chars`·`num_turns`·`web_search_requests`·`web_fetch_requests`, 팩트체크 호출에 `body_hash`·`body_chars` 꼬리표를 더했어요. 새 필드는 배포 이후 호출부터 쌓여요.
- 추가 호출: 제목 점검 2회/편, 판 비교는 조건이 맞을 때만 2회. 둘 다 예산(`can_start_revision`)이 모자라면 기록만 남기고 건너뛰어요.
- 배포 시 `migrate`(office 0023)와 `collectstatic`이 필요해요.

### 2026-11-21 기존 칼럼 재분류

공개·미삭제·비연재 연구팀 칼럼 중 유형이 비어 있던 **68편을 본문 검토 후 심화 53편·실용 15편으로 재분류**했어요. 이미 분류된 8편을 합친 운영 데이터는 심화 57편·실용 19편, 미분류 0편이에요. 본문의 중심이 근거·원리·방법·한계 탐구인지, 실행 절차·계산·선택 기준 제공인지를 기준으로 삼았고 실무 조언이 있다는 이유만으로 실용으로 나누지 않았어요. 분류는 현행 제작 심사를 새로 통과했다는 뜻이 아니에요.

각 글의 사유와 실제 본문 인용은 `column_classified` 감사 기록에 남겼어요. 68개 행을 잠근 단일 트랜잭션에서 제목·본문 지문을 대조하고 유형만 변경했으며, 다른 모든 게시글 필드의 보존과 감사 체인을 확인했어요. 원본 행과 계획·결과는 운영 `backups/column-reclass-20261121T134537308709Z/`에 보존했어요.

후속 코드는 유형 선택지·지도 탭·지도와 상세 링크·관리 원고 카드에서 ‘기존 칼럼’ 분류를 제거해요. 과거 `track=legacy` 주소는 검색 등 다른 조건을 유지한 전체 유형 주소로 301 이동해요. 일반 게시글·연재·과거 제작 기록의 빈 값과 승인 지문은 일괄 변경하지 않아요. 아래 11월 12일 시점의 ‘과거 글은 기존 칼럼으로 표시’ 및 ‘자동 분류 없음’ 설명은 당시 기록이에요. 이번에는 본문 근거를 남긴 명시적 재분류를 수행했어요.

### 2026-11-18 관리자 승인 전환 보완

`office.approval.approve_for_release`가 원고 행 잠금 안에서 작업 중 여부·표시한 검수 버전·기존 승인 정책을 확인하고, 승인과 `ready` 전환을 함께 저장해요. 실패하면 승인 감사 이벤트까지 롤백해요. 일반 승인으로 즉시 공개하지 않으며, 미래 예약은 유지하고 지난 예약은 해제해 수동 공개 대기로 둬요. 예약 없는 `ready`는 `office_release`가 공개하지 않고, 운영자의 별도 ‘지금 공개’가 필요해요. `release_queued` 감사 이벤트에 이전·현재 예약 시각과 승인 번호를 남겨요.

원고 카드에는 일반 승인 차단 사유와 수동 공개 여부를 표시해요. 사실 실패·미완료 수정 요청·남은 필수 수정은 계속 승인을 막고, 예외 승인은 기존 문체·형식 범위만 허용해요. 검증은 `office.test_lab_safety`의 과거·미정·미래 예약, 승인 저장 롤백, 단계·검수 버전 검사와 `office.test_lab_transactions`의 MySQL 동시 승인 검사를 사용해요.

| 공개 시각 (한국 시간) | 분야 | 일반 칼럼 편성 |
|---|---|---|
| 화요일 10:00 | HRD | 심화 1편 + 실용 1편 |
| 목요일 10:00 | 데이터분석 | 심화 1편 + 실용 1편 |
| 토요일 10:00 | 프로그래밍 | 심화 1편 + 실용 1편 |

일반 칼럼은 **주 3편 → 주 6편 편성**이에요. 월요일 교대 연재는 별도이며 변경하지 않았어요. 검수 미달은 해당 유형의 빈 슬롯으로 남기고, 다른 유형 두 편으로 대체하지 않아요.

제작은 기존 전날 준비·재확인·당일 누락 안전망과 10분 단위 공개 흐름을 재사용해요. `office_publish --prepare`/`--if-missing`은 유형 미지정 시 두 유형을 **순차** 준비하므로 동일 제작 cron을 추가하면 안 돼요. 수동 CLI의 유형 미지정은 기존 단편 동작을 보존하고, 관리자 분야별 제작 버튼은 두 유형을 명시해요. 유형별 원고·실행·예산·심사·승인은 독립이에요.

주간 칼럼 회의는 **3분야 × 2유형 = 6개 안건, 각 후보 2개 이상**을 요구해요. 유형 누락·중복·동일 제목 복제는 저장하지 않아요. 기존 회의는 그대로 두고 새 회의부터 이 규칙을 적용해요. 과거 미분류 결정·예약 원고는 전환 시 실용 몫에만 임시 연결해요. 예약의 `분야 × 유형 × UTC 공개 시각` 고유 키로 중복 제작을 막고, 실패한 예약만 같은 원고 ID로 재시도해요.

최종 편집 심사의 `track_review`는 항목별 실제 boolean과 본문의 정확한 인용 10자 이상을 요구해요. 누락·중복·문자열 true·본문에 없는 인용·제목만 인용은 차단해요. **코드가 인용 일치를 검사하는 것과 자료의 학술적 가치·설명의 깊이를 증명하는 것은 달라요.** 후자는 모델 심사와 운영자 검토가 필요해요. 유형을 바꾸면 승인도 다시 받아야 해요.

홈·상세·관리자 화면에서 유형을 표시하고 칼럼 지도에 유형 필터를 제공해요. 과거 글은 빈 `column_track`을 **기존 칼럼**으로 표시해요. 제목만으로 자동 분류하지 않으며, 본문을 검토한 뒤 `classify_columns`에 사유를 남겨 분류해요. 분류는 본문·URL·발행일·조회수를 바꾸지 않아요.

## 4. 글쓰기·관리자 수정 요청 변경

글쓰기 기준은 **독자의 질문과 핵심 답 → 실제 변화 → 근거·원리 → 구체적인 활용 → 반론·한계**예요. 빈 시대 변화 도입, 중복 소제목·결론, 제작 메모를 줄이고 발표일·조사 기준일·버전을 구분해요. 확인하지 않은 경험·실측·인터뷰·벤치마크를 만들지 않아요. 부분 수정에서 이 기준을 이유로 요청 밖 문단을 전면 재작성하지 않아요.

이전에는 전체 재작성 응답을 받은 뒤 요청별 이행 확인 없이 후처리된 원고를 덮어쓸 수 있었어요. 현재는 다음 순서로 처리해요.

1. 원래 요청의 정확한 인용과 완료 기준을 **최대 16개 요구**로 구조화해요. 기존 필수 수정·팩트체크 지적을 참조한 요청에는 실제 지적과 ID를 함께 전달해요.
2. 요구 ID마다 원고에 한 번만 일치하는 `find/replace` 편집을 적용해요. 불일치 편집을 부분 채택하거나 요청 밖 제목을 바꾸지 않아요.
3. 별도 검수 호출이 원래 요청·수정 전후·완료 근거를 대조해요. 작성자의 자기 보고만으로 완료 처리하지 않아요. 미반영·형식 오류는 최대 한 번 보완하며 제공자 한도·호출 오류는 이 반복으로 재시도하지 않아요.
4. 차트 렌더·수치 잠금·연재 자동 보완까지 끝난 **최종 제목·본문**을 다시 확인해요. 도판 삭제를 자동 재생성으로 되돌리지 않으며, 재생성 요청에는 단위·표현 방식·완료 기준을 전달해요.
5. 미반영, 심사 점수 하락, 새 치명 결함·코드 정적 오류·작성 메모, 기존 통과 사실 검증의 실패가 있으면 후보를 채택하지 않아요. **기존 원고·검증·점수·도판을 보존**하고 후보와 사유는 비공개로 남겨요.
6. 저장 직전 행 잠금과 지문 대조로 동시 편집 덮어쓰기를 막아요. 관리자 화면에 요구별 상태·근거·미채택 이유·전후 점수를 보여줘요. 사람 교열본을 다시 쓰지 않는 `--review-only`도 유지해요.

일반 칼럼과 명시적인 관리자 요청이 있는 연재에 적용해요. 점수 하락 차단은 보수적인 채택 정책이며 모델 점수 자체의 일관성이나 실제 품질 상승을 보증하지 않아요. A에서 ‘별도 검수 호출’은 역할·호출 분리이며 **다른 제공자의 독립 검증을 기본화했다는 뜻은 아니에요.**

후처리도 보완했어요. 이미지·링크·인라인 코드의 마크다운 경계를 보존하고, 미확인 도판은 캡션과 함께 통째로 제거해요. 정상 도판·작성자 표·코드는 보존해요. 차트 숫자는 Decimal 자릿값과 쉼표 표기를 유지하고 유효 숫자 6자리 반올림·지수 표기를 없앴어요. 숫자 대조에서 `400`을 `40`의 근거로 인정하지 않아요. 미채택 후보의 심사·호출도 측정하되 최종 통과와 구분해요.

## 5. 운영자 회의 검토 화면 변경

안건별 개별 저장으로 다른 안건의 미저장 선택이 사라지던 폼을 **회의 전체의 한 폼**으로 바꿨어요. 안건마다 후보 하나를 고르고 의견을 쓴 뒤 **선택·의견 한 번에 저장**해요. 일부만 선택하거나 미결정 안건의 의견만 저장할 수도 있어요. 선택 요약·저장됨/미저장/미결정 상태·고정 저장 버튼으로 검토를 도와요. 주제 선택은 원고 게시 승인을 대신하지 않아요.

모든 변경을 먼저 검증하고 한 트랜잭션으로 저장해요. 서명한 버전 지문으로 동시 편집을 검사하며, 손대지 않은 안건의 최신 선택은 덮어쓰지 않아요. 잘못된 선택·300자 초과 의견·충돌 오류 화면에서도 다른 입력을 보존해요. 이미 제작에 쓰인 결정은 잠가요. 반복 저장은 후속 작업·감사·로그를 중복 생성하지 않아요.

운영자 의견은 기획서·설계도·집필에 전달하고, 개발·운영 안건이면 정비 작업 본문에 넣어요. 검증된 사실로 취급하거나 내부 의견을 공개 회의 원문에 섞지 않아요. 변경 시 오래된 공개 소개·요약을 무효화해요. 미저장 입력이 있으면 화면 이탈 경고와 자동 새로고침 억제를 적용하며 브라우저 저장소에 의견을 따로 남기지 않아요.

## 7. 승인·운영·감사에서 유지할 계약

- 기본 흐름은 **제작 → 검수 대기 → 운영자 승인 → 예약 공개**예요. 현재 제목·본문·유형·팩트체크·편집 심사·같은 실행의 순서 있는 단계 근거·이미지 바이트 지문에 승인을 묶어요. 바뀌면 다시 승인해야 해요. 사실 오류·근거 부족·검증 불일치·요청 미이행은 예외 승인으로 우회하지 못해요. 허용된 형식 결함 예외만 사유·OTP 재인증을 요구해요.
- 단계 저장 실패는 제작을 중단해요. 근거가 부족한 기존 보류 원고는 본문을 보존하고 재검증해야 해요. 승인 이미지 원본은 `logs/private-lab/artifacts/<sha256>`에 보존하고 누락·변조 시 차단해요. 공개 차트 제자리 교체 대신 새 파일·검수 원고를 사용해요.
- 승인·예외·취소·공개 사건을 해시 체인으로 기록해요. 앱 관리자·일반 ORM 수정/삭제를 제한하지만 **DB 전체 권한자의 임의 SQL까지 방어하는 감사 체계는 아니에요.** 감사 묶음 복원과 전체 운영 DB 복원도 구분해요.
- `LAB_OPERATOR_IDS`의 활성 운영자만 연구실 관리자·관련 메일 동작을 사용할 수 있어요. 비어 있으면 활성 superuser만 허용해요. 일반 staff의 모델 권한으로 우회하지 못해요. 2026-11-16부터 연구실 관리를 포함한 모든 관리 화면·동작이 같은 OTP 경계(30분, IP 바인딩)를 써요. 만료되면 화면은 재인증으로 이동하고, 만료된 버튼 요청은 처리하지 않으며, 폴링은 403 JSON을 받아요. 공개 JSON에서 내부 회의·운영 안건·미발행 제목을 제외해요.
- `office_work_jobs`와 `office_watch_jobs`는 **서로 독립된 매분 cron**이에요. 작업마다 실행 신원·120초 임대·별도 systemd 사용자 unit·45분 제한·cgroup 종료·umask 0077을 사용해요. 운영은 `LAB_JOB_SUPERVISOR=systemd`, 사용자 linger 활성 상태로 검증했어요. 웹 서비스와 작업 cgroup은 달라요.
- 만료·취소된 실행은 원고뿐 아니라 회의·안건·원장·지도·위클리와 주요 파일을 바꾸지 못해요. 프로세스 종료가 확인되지 않으면 격리해 새 실행을 막아요. `office_job_control status|cancel|restart|resume --job N`으로 명시적으로 다뤄요. 재개는 같은 소스 지문·프로필·유형과 남은 예산이 필요해요.
- 작업용 Django 환경과 모델 CLI 환경을 분리해요. 모델 CLI에는 DB·메일·API 비밀값을 넘기지 않아요. 작업 systemd용 `XDG_RUNTIME_DIR`·`DBUS_SESSION_BUS_ADDRESS` 허용을 모델 환경 허용으로 확대하지 않아요.
- `CLAUDE_BACKEND=cli`, `CLAUDE_CLI_FALLBACK=false`, `AI_ALLOW_PAID_API=false`, `AI_FALLBACK_BACKEND=codex_cli`를 유지해요. 두 구독이 불가하면 보류해요. 사용량 상한은 완료된 호출을 확인해 다음 호출을 막으므로 이미 진행 중인 병렬 호출 때문에 초과할 수 있어요. 토큰을 구독 차감량·금액으로 환산하지 않아요.
- 보존 정책은 실패·보류·실행 중 자료와 감사 기록을 자동 삭제하지 않는 것이에요. `lab_private_cleanup --days 30`은 미리보기이며 `--apply`는 실제 변경이에요. 이번 문서 통합은 로그·백업·증거·외부 메모리 정리가 아니에요.

운영 기준 경로는 `/home/ubuntu/projects/mysite`, 인터프리터는 `/home/ubuntu/venvs/mysite/bin/python3`, 설정은 `config.settings.prod`, 서비스는 `mysite`예요. 접속·인증 정보는 이 문서에 복사하지 않아요. 배포·재시작·push·DB 적용은 사용자의 해당 작업 요청이 있을 때만 수행해요.

## 8. 검증 근거와 한계

### 자동 검사·CI

## 9. 후속 검토와 점검 명령

가장 먼저 볼 것은 새 편성의 **실제 심화·실용 한 쌍**이에요. 심화의 1차 자료·원리·비교·한계, 실용의 절차·적용 조건, 운영자 의견과 수정 요구 반영을 사람이 확인해요. 그 뒤 유형별 미채택 이유·심사/수정 횟수·호출량·검수 시간·유용성을 기록해요. 조회수만으로 심화 편성을 축소하지 않아요.

추가로 남은 검증은 운영과 같은 Ubuntu에서 실행 중 웹 재시작·워커 종료·DB 장애·취소 후 회수, 전체 DB/미디어/설정 복원 훈련이에요. 코드·설정·복원 검증 없이 완료로 표시하지 않아요. B 전환은 현재 작업 목표가 아니에요.

로컬에서 모델 호출 없이 확인하는 명령이에요. Windows는 `python` 대신 `py -3.10`을 사용해요.

```powershell
py -3.10 manage.py check
py -3.10 manage.py makemigrations --check --dry-run
py -3.10 manage.py showmigrations community office
py -3.10 manage.py classify_columns
py -3.10 manage.py lab_audit
git diff --check
```

감사 `--export --restore-check`와 품질 보고서의 `--output`은 비공개 파일을 생성해요. `office_job_control`은 `status` 외에는 작업을 변경해요. `office_publish`, `office_revise`, `lab_pilot --execute`는 실제 구독을 사용하므로 공지 확인을 위해 무심코 실행하지 않아요. 원고 재심·제작·분류는 목적과 대상이 정해진 후 수행해요.

운영 롤백이 필요하면 신규 등록과 실행·공개 cron을 먼저 멈추고 프로세스 종료를 확인해요. DB 필드를 즉시 제거하거나 과거 코드로 공개 cron을 그대로 돌리지 않아요. 위 백업의 DB·미디어·환경·cron·서비스와 코드 호환성을 함께 검토하고, 이미 승인·공개한 글과 감사 이력을 보존해요.
