# 단일 관리자용 연구실 고도화

판매·고객별 배포·납기 보장은 범위에 없어요. 기존 DB에 적용하기 전 마이그레이션과 실행기 설정을 확인해야 해요.

확인한 테스트와 실환경 검증의 한계는 [2026-11-10 검증 기록](lab-operator-validation-20261110.md)에 정리했어요.
후속 CTO 재평가의 우선순위와 최신 실행 결과는 [실행 계획](lab-priority-execution-20261110.md)을 우선해요.

## 발행과 감사

일반 승인은 현재 제목·본문의 사실 검증과 편집 심사를 모두 통과해야 해요. 예외 승인은 문체·분량 등 형식 결함만 허용하며, 사유와 OTP 재인증이 필요해요. 사실 오류·근거 부족·검증 불일치는 사유로 우회할 수 없어요.

승인은 제목·본문·팩트체크·편집 보고·현재 실행의 단계별 근거에 묶여요. 근거가 바뀌거나 수정 지시·반려가 있으면 승인이 무효화돼요. 승인·예외·취소·공개 사건은 별도 해시 체인에 저장해요. 관리자 화면과 일반 ORM 수정·삭제는 차단하지만 DB 전체 권한을 가진 사람의 조작까지 방어한다고 주장하지 않아요.

승인 폼에는 화면에 표시한 버전의 지문도 들어가요. 화면을 연 뒤 본문·심사·근거가 바뀌면 승인과 즉시 공개를 거절해요. 새로고침으로 변경 내용을 확인해야 다시 승인할 수 있어요.

현재 원고의 검증·심사·최종 기록이 같은 실행에 순서대로 있어야 해요. 단계 저장 실패는 제작을 중단해요. 최종 기록은 제목·본문·검증 보고·편집 보고의 지문에 묶이고, 단계 누락·최종 기록 이후 새 단계·새 제작 실행은 승인을 차단해요. 기록이 부족한 기존 원고는 본문을 보존한 채 `office_revise --draft N --review-only --no-publish --note "현재 원고 재검증"` 등으로 검증·심사를 다시 실행해야 해요. 기존 승인과 공개 대기 원고를 자동으로 새 정책에 맞췄다고 처리하지 않아요.

차트와 본문의 로컬 이미지 파일은 실제 바이트 해시·크기를 승인 스냅샷에 넣어요. 승인 때 `logs/private-lab/artifacts/<sha256>`에 원본을 보관해요. 파일 변경·누락·보관본 손상은 승인을 무효화해요. 새 차트는 내용 해시가 파일명이고, `redraw_chart`도 새 검수 대기 원고를 만들어요. 공개 파일을 제자리에서 교체하지 않아요. 승인 대상 이미지는 관리되는 미디어 저장소에 보관해야 해요.

`lab_audit --export --restore-check`는 체인을 검증하고 `logs/private-lab/`에 백업해요. 직렬화한 감사 자료와 승인 파일 보관본을 별도 SQLite 파일 DB·임시 파일 저장소에 복원한 뒤 해시와 개수를 대조해요. 보관본 누락도 실패로 처리해요. 이 시험은 전체 운영 MySQL·미디어 복원 훈련을 대신하지 않아요.

## 실행과 복구

- `office_work_jobs`: 기존 1분 작업 실행기예요. 작업 실행 번호·프로세스 시작 신원·120초 임대를 사용해요.
- `office_watch_jobs`: 실행기와 다른 cron/timer로 매분 실행해요. 만료·종료 작업을 확인하고, 종료를 확인할 수 없으면 격리해 새 작업을 막아요.
- 운영 Ubuntu에서는 `LAB_JOB_SUPERVISOR=systemd`로 설정하고 사용자 systemd 세션·linger·EnvironmentFile(.env) 호환성을 확인해요. 작업마다 별도 unit의 45분 제한과 cgroup 종료를 사용해요. 로컬 process 모드는 같은 수준의 OS 격리를 보장하지 않아요.
- `office_job_control status|cancel|restart|resume --job N`: 원고 상태와 실행 상태 확인, 명시적 취소·새 실행·일반 칼럼 체크포인트 재개예요. 종료 미확인 작업은 바로 재시작하지 않아요.
- 재개는 소스 지문과 프로필이 같아야 해요. 다른 버전이거나 예산이 소진됐으면 확인 후 새 실행을 선택해요. A/B 모두 호출·시간 예산을 적용해요. 독립적인 편집 심사 표본은 캐시 키도 구분해요.

임대가 만료되거나 실행 번호가 바뀐 작업은 원고 저장·단계 기록·발행을 할 수 없어요. 운영자 권한을 잃은 계정의 대기 작업도 취소돼요. 배포 전에 기존 구식 실행을 종료하고 대기열을 확인해야 해요.

회의·안건·활동 로그·원장·칼럼 지도·위클리·설정의 모델 저장/삭제와 QuerySet update/delete/bulk 변경에도 실행 행 잠금을 적용해요. 회의·안건 저장 실패는 함께 롤백돼요. 체크포인트와 주요 이미지 게시에도 실행 권한을 검사해요. 위클리 카드의 판본별 해시 디렉터리는 취소된 제작이 기존 공개 이미지를 덮어쓰지 않게 해요. 임시 렌더 파일과 실제 공개 파일을 구분해요. 일반 ORM과 허용된 명령 경계의 보호이며 DB 전체 권한의 임의 SQL을 보안 경계로 취급하지 않아요.

프로세스를 만든 뒤 신원 확인 등에서 오류가 생겨도 실행 PID를 보존하고 격리해요. 시간 초과도 프로세스 트리의 종료가 확인돼야 대기열을 풀어요. Linux 좀비는 종료된 프로세스로 구분해요.

## 접근·파일·로그

`LAB_OPERATOR_IDS`에 운영자 계정 ID를 지정해요. 비어 있으면 활성 superuser만 허용해요. 일반 회원·일반 staff·비활성 계정은 관리자 및 메일 링크에 접근할 수 없어요. Django 기본 관리자에서도 연구실 모델에 같은 제한을 적용해요. office 모델 권한만 받은 staff도 운영자 허용 목록을 우회할 수 없어요. 원본 CLI 작업 로그와 감사 내보내기는 기존 OTP 재인증도 요구해요.

메일 링크는 인증 후 실행하며 같은 링크로 완료된 작업을 다시 만들지 않아요. 작업은 명령과 인자 허용 목록으로 검사해요. 모델 CLI에는 DB·메일·API 비밀값을 전달하지 않아요. 작업용 Django 프로세스의 DB 설정과 모델 CLI의 환경을 분리해요. 운영 생성 코드 실행과 유료 API는 계속 차단해요.

공개 상태 JSON은 내부 회의 원문·운영 안건·미발행 원고 제목을 내보내지 않아요. 이전에 다듬어 둔 공개 문장도 미발행 원고에는 그대로 사용하지 않아요.

`lab_isolation_probe --base-url https://techchang.com`은 HEAD와 GET의 응답 헤더만 확인해요. 파일 본문을 읽거나 출력하지 않아요. Nginx에는 `/logs/`, `/backups/`, `/scratchpad/`, `/tmp/`, `/.env`, `/.git` 등의 직접 접근 차단이 필요해요. 현재 상태 점검과 새 코드 배포 검증은 구분해요.

`lab_private_cleanup --days 30`은 정리 대상만 보여요. `--apply`를 명시해야 공개·반려된 원고의 오래된 체크포인트를 삭제해요. 실패·보류·실행 중 자료와 감사 기록은 자동 삭제하지 않아요. 로그는 기존 logrotate 정책을 확인해요.

## 품질과 사용량

`lab_pilot --output logs/private-lab/pilot --rounds 2`는 총 12편 목록을 만들어요. `--execute`로 실제 구독을 사용해요. `--case 1-1-a`처럼 한 사례를 지정할 수 있어요. 실제 기획부터 수행하고, 코드 실행은 운영과 같이 기본 꺼짐이에요. 기존 결과를 덮어쓰지 않아요.

`--freeze`는 모델 호출 없이 목록과 소스 지문을 먼저 고정해요. 현재 목록은 코딩·데이터·HRD 각 1개 기획의 A/B 2회 반복이에요. 두 번째 반복은 B→A 순서로 실행해요. 각 사례의 테스트 DB를 초기화해 원장·모델 공급자 상태를 공유하지 않고, 이미지도 사례의 비공개 미디어 폴더에 저장해요. 구독 제공자 오류가 나면 실패 자료를 보존하고 배치를 중단해요.

블라인드 번호는 목록 생성 때 고정돼요. 전체 실행을 재개하면 완료 사례를 건너뛰고 기존 사람 평가를 보존해요. 설정이나 소스 지문이 달라지면 같은 폴더의 실증을 이어 붙이지 않아요. 원고에는 제목도 포함해요. 임시 DB의 기존 칼럼 이력은 비어 있으므로 이 결과로 운영 글과의 중복 방어를 검증했다고 판단하지 않아요.

평가자에게는 `blind/` 폴더와 `blind/review.json`을 제공해요. 평가표에는 프로필·사례 대응표를 넣지 않아요. 이미지도 블라인드 폴더에 함께 있어요. `lab_pilot_report --input .../blind/review.json`은 관리자 평가가 모두 있어야 비교해요. 원고·단계 JSON·소스·실행 UUID·이미지·블라인드 원고·평가 지문을 대조하고, 원본 자료 없는 평가 JSON은 거절해요. 빈 원고·중단도 실패 표본으로 포함해야 해요. 효용과 검수 시간, 전체 시도 호출·사용량을 함께 봐요. 토큰을 구독 차감량이나 금액으로 단정하지 않아요. B는 관리자 검수 결과가 나오기 전에 기본값으로 전환하지 않아요.

## 적용 순서와 남은 운영 검증

1. 관련 테스트·Django check·마이그레이션 일관성을 확인해요.
2. 사용자 적용 요청 때 백업 후 0017~0020을 적용해요. 기존 0015·0016 미적용 환경은 함께 필요해요.
3. 진행 중 작업을 비우고 운영자 ID, 독립 감시 timer와 systemd 실행기 설정을 반영해요.
4. 가짜 작업으로 웹 재시작·실행기 강제 종료·DB 중단·취소를 실제 운영과 같은 Ubuntu 환경에서 확인해요.
5. MySQL CI 행 잠금 시험, 전체 DB·미디어 복원 훈련, 12편 실제 생성과 관리자 평가를 따로 기록해요.

운영 설정 변경과 DB 적용은 이 문서 작성만으로 수행하지 않아요. 재개 소스 지문, 승인 정책 변경, 운영자 한정 접근과 독립 감시는 Claude 메모리에 남길 결정이에요.
