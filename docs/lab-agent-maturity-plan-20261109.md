# 연구실 AI Agent 고도화 계획 (2026-11-09)

> 최초 계획의 이력이에요. 이후 확정한 단일 관리자 범위와 발행·복구·감사 정책은 [현행 운영 문서](lab-operator-hardening.md)를 우선해요. 판매·납기 목표는 현행 범위에서 제외됐어요.

## 목표와 현행 기준

목표는 연구원 수나 심사 점수를 늘리는 것이 아니라, **검증되지 않은 글을 자동 공개하지 않으면서** 정해진 시간 안에 유용한 글을 안정적으로 만드는 것이다. 저장소 기본 프로필은 A이고 B는 선택형이다. 운영 서버의 실제 스위치 값과 성과는 별도로 확인해야 한다.

현재 위험은 다음 순서로 처리한다.

1. A에서 사실 검증이 미통과이거나 심사 뒤 원고가 바뀌어도 편집장 판정만으로 발행될 수 있는 경로를 닫는다.
2. 관리 화면에서 시작한 긴 작업이 웹 서비스 재시작에 함께 종료되는 결합을 끊는다.
3. 모델 자체 심사 통과율과 실제 발행·사람 검수 결과를 구분해 측정한다.
4. 같은 모델의 역할 분리를 독립 검증으로 과대평가하지 않는다. B는 근거·완성률·사용량을 측정한 뒤에만 기본값으로 전환한다.

## 단계별 작업

### 1. 발행 안전성 — 즉시

- A와 B 모두 최종 원고의 제목·본문 버전과 사실 검증 `pass`가 맞아야 자동 발행한다. 편집 점수·재심 판정은 사실 관문을 우회하지 못한다.
- 심사 뒤 본문 또는 제목이 바뀌면 수치 변화 여부와 관계없이 재검증한다. 도판 전용 변경은 기존의 정규화 해시 규칙을 따른다.
- 운영자가 명시적으로 승인한 수동 발행은 유지하고, 자동 발행과 별도로 기록한다.
- 검증: 미통과·오래된 검증은 보류, 현재 검증만 공개 대기/발행되는 통합 테스트.

### 2. 작업 실행 안정성 — 다음 배포 전

- 웹 요청과 저장 신호는 작업을 DB 대기열에 기록한다. 별도 1분 cron의 `office_work_jobs`가 작업을 시작해 웹 서비스 재시작의 프로세스 그룹에서 분리한다. 기존 10분 공개 cron은 공개만 담당한다.
- 대기·실행·실패 상태를 구별하고 중복 클릭과 프로세스 시작 실패를 처리한다. 재시작 중 끊긴 작업의 기존 복구 규칙은 유지한다.
- 배포 전 운영 cron·서비스 구성을 확인한다. 운영 설정 변경과 배포는 별도 요청 때만 한다.

### 3. 품질 측정 — 같은 배포에 포함

- 30일 보고서에 프로필, 첫 검증 통과, 최종 발행 상태, 보류 사유, 사용량의 분포와 측정 불가 항목을 포함한다.
- 별도 사람 평가표에서 사실 오류, 정정, 독자 효용, 검수 시간을 기록한다. 모델 점수는 사람 평가의 대리 지표로 쓰지 않는다.
- 비교 단위는 같은 주제·장르의 A/B 원고다. 최소 3개 주제와 통계·튜토리얼 장르를 포함하고, 검증 기준을 낮추지 않는다.

### 4. B 전환 결정 — 파일럿 이후

- B 파일럿의 사전 기준: 자동 발행 가능률, 사람 확인 사실 오류, 운영자 검수 시간, 1편당 토큰·시간, 예약 시각 준수율을 A와 비교한다.
- 코드 실행 검증은 OS 수준 격리가 생기기 전까지 운영 서버에서 켜지 않는다.
- 구독 한도·실행 예산을 넘으면 보류한다. 유료 API·서버 `crew_work`로 우회하지 않는다.
- B가 기준에 못 미치면 A를 유지하면서 원장 수집·집필 지시·부분 수정의 실패 원인을 좁혀 고친다.

## 완료 조건

- 자동 발행 경로에 사실 검증 미통과 또는 버전 불일치가 남지 않는다.
- 관리자 작업이 웹 서비스 재시작에 의해 중단되지 않는다(운영 구성 확인 필요).
- 보고서가 모델 심사와 실제 공개·사람 검수 결과를 혼동하지 않는다.
- B 전환 여부는 파일럿 데이터와 운영자 검수 결과로 결정한다. 파일럿 미통과 상태에서 기본 프로필을 바꾸지 않는다.
