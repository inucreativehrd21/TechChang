# 심화 탐구와 실용 팁의 독립 편성

운영자 요청은 기존 발행 주기를 유지하면서 **학술·기술 트렌드·심화 탐구 1편 + 일상·실용 팁 1편**, 총 2편을 편성하는 거예요. 분야(HRD·데이터분석·프로그래밍)와 편집 유형을 별도 축으로 두었어요. 정기 연재는 기존 주기를 유지해요. B 기본 전환 보류와 구독 CLI 전용 정책도 유지해요.

운영 적용 전, 여섯 칼럼 안건을 한 번에 검토·선택·의견 저장할 수 있도록 [회의 선택 화면도 보완했어요](lab-meeting-decision-review-20261112.md).

## 문제와 편집 원칙

기존 회의 지시는 검색 유입 확대를 최우선으로 두고, 안건 선택지를 수요순으로 재정렬했어요. 기술·학술적 중요성이 높지만 검색량이 작은 질문이 실용 소재에 밀릴 수 있는 구조였어요. 전체 최근 발행물의 본문을 전수 심사해 비율을 계산한 진단은 아니며, 코드의 선정 편향을 확인한 결과예요.

| 구분 | 학술·기술 심화 (`research`) | 일상·실용 팁 (`practical`) |
|---|---|---|
| 중심 질문 | 왜 동작하고 무엇이 달라졌으며 어디까지 설명할 수 있는가 | 내 문제에 무엇을 어떻게 적용하면 되는가 |
| 주제 선정 | 연구·기술적 중요성, 설명할 원리, 검증 가능한 1차 자료 | 실제 문제와 효용, 적용 대상, 검색 수요 참고 |
| 근거 | 논문·공식 기술 문서·표준·원자료 2개 이상을 대조하도록 기획·심사 | 공식 제도·문서·자료, 구분해서 표시한 가정 예시와 계산 |
| 필수 내용 | 탐구 질문, 근거·방법, 동작 원리, 대안 비교와 한계 | 구체적 문제, 실행 절차·계산·선택 기준, 적용 조건·예외 |
| 최신성 | 실제 기술 변화는 발표일·버전·기존 대비 변화를 확인. 기초 탐구에 최신 유행을 꾸미지 않음 | 제도·도구의 기준일과 적용 시점을 확인 |
| 탈락 사례 | 뉴스 요약, 논문 제목 나열, 생활 팁을 심화로 재포장, 검증하지 않은 벤치마크 | 근거 없는 요령, 대상·예외가 없는 단정, 심화 글을 단순 요약한 중복 글 |

학술 주제만 매번 강제하지는 않아요. 연구 방법, 실제 기술 트렌드 분석, 기초 원리의 심화 탐구가 첫 유형에 함께 들어가요. 심화의 유용성은 즉시 따라 할 체크리스트뿐 아니라 연구·설계 판단 기준과 열린 질문도 포함해요. 통계가 없는 주제에 숫자를 만들도록 요구하지 않으며, 출처 있는 방법·스펙 비교표도 근거로 받아요.

기존 카드 배분 칼럼 #137은 본문 중심이 계산·선택 절차이므로 실용 유형에 해당하는 사례예요. 이번 작업에서 운영 DB의 분류 값을 바꾸지는 않았어요.

## 발행 편성

| 공개일·시각 | 분야 | 기존 | 변경 |
|---|---|---|---|
| 화요일 10시 | HRD | 1편 | 심화 1편 + 실용 1편 |
| 목요일 10시 | 데이터분석 | 1편 | 심화 1편 + 실용 1편 |
| 토요일 10시 | 프로그래밍 | 1편 | 심화 1편 + 실용 1편 |

일반 칼럼은 주 3편에서 **주 6편 편성**이 돼요. 월요일 정기 연재는 별도예요. 이는 검수 통과를 전제로 한 편성이며, 심사·사실 검증·운영자 승인 기준을 낮춰 매번 2편을 강제 공개하지 않아요.

기존 전날 13·22시 준비, 당일 4시 재확인, 10시 누락 안전망, 10분 단위 공개 흐름을 재사용해요. 예약 명령에 유형을 지정하지 않으면 두 유형을 순차 실행하므로 cron에 같은 제작 명령을 한 줄 더 추가하지 않아요. 두 유형은 각각 실행 ID·호출 예산·원고·심사·승인을 가져요. 한쪽의 보류·실패는 다른 쪽의 슬롯을 채우거나 이미 만든 글을 되돌리지 않아요. 구독 부족이면 해당 원고를 보류하며 유료 API를 켜지 않아요. 제작량 증가에 따른 구독 사용량과 실제 심화 품질은 운영 표본으로 추가 평가해야 해요.

## 구현한 흐름

1. 트렌드 정찰의 기존 호출에서 분야마다 심화 2개·실용 2개 후보를 요청해요. 심화 후보의 연구 가치 순서는 유지하고 실용만 검색 수요순으로 정렬해요. 주간 회의 결과에는 3개 분야 × 2개 유형 = **6개 독립 안건**, 각각 선택지 2개 이상이 필요해요. 유형 누락·중복·동일 제목 복제를 검사하고 잘못된 응답은 저장하지 않아요.
2. 결정·작업 원고·게시글에 `column_track`을 저장해요. 심화 제작에 실용 안건을 소비하지 않아요. 과거의 미분류 결정은 실용 제작에서만 임시로 사용하고, 미분류 예약 원고도 실용 몫에만 포함해 전환 시 3편이 생기는 것을 줄여요.
3. 예약은 `분야 × 유형 × 공개 시각`의 고유 `slot_key`로 한 번만 확보해요. 키는 UTC로 정규화하고 DB unique로 중복 생성을 막아요. 이미 준비·보류·제작 중인 유형은 건너뛰고 실패한 예약만 같은 원고 ID로 다시 제작해요. 다른 유형의 체크포인트로 재개하지 못해요.
4. 기존 호출 경계에 유형 지침을 전달해 기획·집필·팩트체크·평론·시각화·수정을 연결해요. 병렬 단계도 기존 ContextVar 전달을 사용해요. 별도 연구실 에이전트나 유료 API 호출 경로를 추가하지 않았어요.
5. 심화 글에는 전용 구조와 심사 설명을 적용해요. `탐구 질문 → 근거와 방법 → 동작 원리 → 비교와 한계 → 시사점 → 맺음말 → 참고 자료`로 탐구를 이어 가요. 모범 칼럼도 같은 유형 안에서만 고르며, 심화 모범이 없다고 실용 글을 심화의 기준으로 제시하지 않아요.
6. 기존 독립 편집 심사에서 `track_review`를 함께 받아요. 필수 항목별 true/false와 최종 본문의 정확한 인용을 요구하고, 누락·중복·문자열 true·없는 인용·제목만 인용을 차단해요. 실패하면 `editorial_mismatch`로 보류해요. 인용 일치는 코드로 확인하지만 자료의 학술적 가치·설명의 깊이는 독립 모델 심사와 운영자 검토가 판단해요.
7. 승인 시 원고 유형과 심사 유형이 같아야 하고 유형별 근거가 유효해야 해요. 유형 변경도 승인 스냅샷을 바꾸므로 기존 승인을 재사용하지 못해요. 관리자 부분 수정과 발행 글 리메이크도 저장된 유형을 이어 받아요.
8. 홈 목록·상세·관리자 화면에 유형을 표시하고 칼럼 지도에 유형 필터를 추가했어요. PC·모바일에서 검색과 함께 사용하며, PDF 인쇄 머리에도 유형 조건을 남겨요. 품질 보고서에는 두 유형과 기존 실행의 지표를 따로 담아요.

## 기존 칼럼 분류

기존 행의 기본값은 빈 값이며 화면에서는 **기존 칼럼**으로 보여요. 제목·키워드만으로 학술성을 자동 판정하거나 본문을 일괄 재작성하지 않아요. 본문 중심 질문과 근거를 검토한 뒤 아래 명령으로 분류하고, 사유를 감사 기록에 남겨요. 분류는 본문·발행일·조회수·URL을 바꾸지 않아요. 연재는 별도 분류이므로 이 명령 대상에서 제외해요.

```powershell
# 읽기 전용 목록
py -3.10 manage.py classify_columns
# 실제 본문을 검토한 글만 분류 (운영에서는 배포 후 운영 환경의 인터프리터로 실행)
py -3.10 manage.py classify_columns --question 137 --track practical --reason "본문 중심이 카드 배분의 계산·선택 절차예요."
```

이 예제의 운영 분류 명령은 실행하지 않았어요.

## 실행과 전환 순서

```powershell
# 같은 공개일에 두 유형 준비 (기존 cron도 이 기본 동작)
py -3.10 manage.py office_publish --topic data --prepare
# 실패한 유형만 지정해서 확인·준비
py -3.10 manage.py office_publish --topic data --track research --prepare
# 별도 시각 예약 없이 수동 제작하려면 유형을 명시
py -3.10 manage.py office_publish --topic coding --track research --no-publish
```

관리자 화면의 분야별 제작 버튼도 두 유형 각 1편을 예약해요. CLI의 기존 수동 제작·동결된 파일럿은 유형 미지정 시 기존 단편 동작을 유지해요. `--track both`는 명시적으로 두 편을 제작하고 `--track legacy`는 과거 유형을 유지해요. 유형별 재개에는 해당 `--track`과 `--resume-run`을 함께 써요.

운영 전환 순서는 **기존 미배포 운영·감사 변경과 함께 배포 범위 확정 → DB 백업 → community 0056·office 0021을 포함한 마이그레이션 적용 → 코드·웹 반영 → 첫 심화/실용 한 쌍 검수 → 기존 칼럼의 본문 검토·분류**예요. office 0021은 community 0056에 의존해 두 스키마의 순서도 연결했어요. 이전 체크포인트는 소스 지문이 달라 새 코드로 그대로 재개할 수 없어요. 이미 제작 중인 작업과 남아 있는 예약을 먼저 확인해야 해요.

검수 미달은 그 유형의 빈 슬롯으로 남기고 다른 유형 2편으로 대체하지 않아요. 초기 운영에서는 두 유형의 요청 이행률·미채택 사유·심사 횟수·호출량·독자 유용성을 따로 보고, 조회수만으로 심화 편성을 축소하지 않아요.

## 검증과 현재 상태

로컬 구현과 자동 검사·화면 확인을 완료했어요. **운영 코드 배포·재시작·운영 DB 마이그레이션·기존 글 일괄 분류는 하지 않았어요.** 새 필드를 준비하는 마이그레이션 파일만 생성했으며 개발 DB에도 임의 적용하지 않았어요. 실제 구독 모델로 심화·실용 한 쌍을 새로 제작하는 실증은 이번 작업에 포함하지 않았어요.

회귀 검사는 `office`, `common`, 공개 칼럼 지도·홈 검사 **747개에서 실패 0, MySQL 전용 3개 제외**였어요. 관리자 버튼 보완 후 관련 48개도 모두 통과했어요. 두 검사 묶음은 겹치므로 합산하지 않아요. 이후 지표 집계에서 실행 메타데이터가 없는 과거 기록도 기존 유형에 포함하는 보완을 추가하고 별도 검사했어요. Django check, 마이그레이션 상태 검사, diff 검사도 확인했어요.

근거 로그는 `logs/lab-editorial-tracks-final-regression-20261112.log`, `logs/lab-editorial-tracks-admin-final-20261112.log`, `logs/lab-editorial-tracks-metrics-final-20261112.log`예요. 슬롯 고유성과 재시도는 SQLite에서 확인했으며 MySQL 동시 실행을 이번 변경으로 새로 실증한 것은 아니에요.

PC 1280px·모바일 390px의 실제 템플릿 분기를 fixture로 확인했어요. 모바일 User-Agent·`force_version=mobile`·`header.m-header`·`nav.m-tabbar`로 모바일 분기를 대조했고 가로 넘침이 없었어요. 유형 필터 클릭, 결과 한 편으로 제한, 검색 후 유형 유지도 두 화면에서 확인했어요. 화면 자료는 `scratchpad/lab-editorial-tracks-desktop.png`, `scratchpad/lab-editorial-tracks-mobile.png`예요. 운영 데이터나 새 글의 내용 품질 검증을 대신하지 않아요.

Claude 메모리에 남길 결정은 “분야와 편집 유형을 분리”, “정기 발행일마다 심화·실용 각 1편”, “심화의 검색 수요 순위 제외”, “기존 글은 본문 검토 후 분류”예요. 저장소 밖 메모리는 수정하지 않았어요.
