# 연구실 A안 → B안 · 3D A안 구현 기록

2026-10-30 제안서 8쪽의 연구 구조를 순서대로 구현해요. 서버 배포·재시작·원격 push·운영 DB 적용은 포함하지 않아요.

## 단계

1. A: 역할별 모델 상향, 기존 구독 폴백 보존, 모델을 명시하는 비공개 평가
2. B: 작성과 독립 검증의 제공자 분리, 주장별 원문·수치 계약, 결함 ID와 변경분 재심
3. B: 동일 원고의 병렬 검토, 조건부 조사, 실행 예산·체크포인트·회복, 통합 평가
4. 3D A: 방 하나·공유 캐릭터 리그·공개 상태 연동·선택형 모바일 3D

2026-10-31: A 경로와 B 경로를 로컬에서 구현했어요. 기본 프로필은 A이며, B는 `--profile b` 또는 `OFFICE_MODEL_PROFILE=b`로 선택해요. 운영 환경은 바꾸지 않았어요. 공식 모델 지원과 실제 계정 사용 가능 여부는 구분해요.

## 모델 프로필

`OFFICE_MODEL_PROFILE=legacy|a|b`로 연구실에만 적용해요. 사이트 전체 Claude 기본값과 기존 Codex 장애 폴백 모델은 유지해요.

- legacy: 기존 Sonnet 5.5와 한도 오류 시 Codex 폴백
- a: 기획·집필·검증·편집 Opus 5.5, 도판 Sonnet 5.5. 기존 한도 폴백
- b: 기획·집필·편집 Opus 5.5, 독립 검증·중재 Sol high(2026-10-31 Astra high에서 변경 — 한 편에 Codex 한도 절반 가까이 사용), 근거 수집·조사·도판 Sol medium. 독립 검증은 다른 제공자로 우회하지 않아요.

평가에는 `evaluate_subscriptions --backend routed --profile a|b --cases ... --output-dir ...`를 사용해요. 모델을 직접 비교할 때는 `--backend claude|codex --model MODEL_ID`를 사용해요. DB·메일·공개 원고를 바꾸지 않으며 실제 구독 사용량은 들어요.

## B안 구현

- 자료가 부족한 주장에만 공개 명부와 별개인 조사 워커를 최대 2개 실행해요. 공개 연구원은 8명을 유지해요.
- 설계도와 완성 원고가 같은 주장 계약을 사용해요. claim/source ID, 원문 위치·인용 hash, 대상·기간·발행일·지지 여부를 기록해요. 확인 실패를 검증 통과로 바꾸지 않아요.
- 숫자는 Decimal의 자릿값을 보존하고 규모·통화를 포함한 단위를 대조해요. 45.64와 4.564, 원과 달러, 다른 시점을 같은 근거로 간주하지 않아요.
- 같은 원고의 검증·평론·도판 계획을 최대 2워커로 읽고, 본문·도판 반영과 콘텐츠 기록은 메인 실행자가 담당해요. 제공자 상태와 구독 잠금은 기존 계층을 사용해요.
- B안에서는 점수 근처의 동일 심사 3회를 제거했어요. 사실 검증이 통과했지만 평론 거절과 높은 편집 점수가 충돌할 때만 Astra가 1회 중재해요. 원고 인용이 없으면 기존 차단을 유지해요.
- 필수 결함에 안정된 issue_id를 부여하고, 재심에서 모든 이전 결함에 대한 해결 여부·근거를 요구해요. 누락·문자열 true·근거 없는 해결 판정은 차단해요.
- B안은 필수 결함이 없고 독립 검증이 끝난 minor(65점 이상)를 불필요한 빈 수정 없이 수리해요. 낮은 점수·치명 결함·미해결 결함은 차단하며 프리미엄 점수 기준은 바꾸지 않아요.
- 수정은 패치를 우선하고 B안에서는 패치 실패를 전체 재작성으로 확대하지 않아요. 원문 URL·코드가 바뀌면 전체 검증, 보존 가능한 문자 그대로의 주장과 작은 변경만 변경분 검증을 허용해요.
- 실제 시운전에서 상류 자동 점검·팩트체크·편집 심사가 각각 재작성을 유발하는 낭비를 확인했어요. B는 자동 점검·팩트체크·평론의 지적을 첫 통합 심사에 모아 부분 수정 1회로 처리해요. 사실 검증이 미달이면 도판 모델 호출도 미뤄요. 검증 뒤 문장을 자동 삭제해 다른 부분을 무너뜨리는 경로는 B에서 사용하지 않아요.
- 자동 발행은 현재 원고 hash와 독립 검증의 버전이 같아야 해요. 발행은 행 잠금과 트랜잭션으로 중복 실행을 막아요. 기존 운영자의 명시적 검수·수동 발행 권한은 유지하며 모델 응답만으로 이 권한을 얻을 수 없어요.
- 전체 실행 24회·2,400초의 초기 예산을 적용해요. 한도/근거/독립 검토 미완료는 보류하며 유료 API로 우회하지 않아요. 공개 전 제목 재생성도 생략해 검증 뒤 새 주장이 들어오지 않게 해요.
- 저장하는 칼럼 실행의 비공개 응답 체크포인트는 `logs/lab-runs/<UUID>.json`이에요. 같은 모델·도구·프롬프트·출력 예산일 때만 재사용해요. `office_publish --profile b --topic coding --resume-run UUID`로 재개할 수 있어요. 같은 UUID는 동시에 실행하지 못해요.
- 연재·리메이크·운영자 수정도 실행 예산과 새 검증 규약을 사용해요. 현재 CLI 체크포인트 재개는 일반 칼럼 제작에만 제공해요.
- 회의는 분야별 독립 제안 3개와 고정된 제안에 대한 검토로 바꾸고, 최종 심사자인 편집장은 기획 조율에 참여하지 않아요. B의 기본 회의 호출은 15회 발언+종합에서 7회 발언+종합으로 줄어요(트렌드 조사 등은 별도예요).

## 검증과 남은 관측

- Opus 5.5·Astra high의 실제 구독 CLI 스모크 테스트 각각 1/1 통과
- B 역할 배치의 집필·편집·웹 확인 고정 입력 3/3 통과. 웹 확인은 실제 웹 도구 이벤트 2건과 공식 Django URL을 확인했어요.
- `--suite research`: 값·규모·통화·기간·모집단·인과·근거 누락·필수 결함·버전의 고정 경계 사례 12/12 통과
- 최종 연구실 및 구독 어댑터 회귀 423개 통과(31.05초). 독립 검증·발행 버전·필수 결함·보류 경로를 포함해요.
- Django check 통과, `makemigrations --check --dry-run`: 변경 없음. DB 적용은 하지 않았어요.
- 고정 사례 통과를 실제 칼럼의 첫 심사 통과율·재심 감소율로 보고하지 않아요. 과거 30편의 층화 비교와 사람의 블라인드 평가는 아직 하지 않았어요.

실제 구독으로 Django 관계 조회 글 1편을 임시 테스트 DB에서 비공개 dry-run 했어요. 1,610.9초·24회 호출 뒤 예산 한도로 중단됐어요. 마지막 편집 판정은 75점·major, 필수 수정 7건, 독립 검증 미완료였어요. 발행이나 업무 DB 변경은 하지 않았어요. 이 결과는 성공한 칼럼 생성으로 세지 않아요. 원문 확인의 큰 입력과 중복 수정이 병목이었고, 이후 통합 지적→부분 수정 1회·같은 실행의 근거 재사용·검증 실패 시 후속 평론/도판 중단으로 조정했어요. 명시적인 Django/Python 제품 버전을 통계 수치로 오인하던 자동 점검도 수정했어요. 조정 후 회귀 검사는 통과했지만 새 글을 처음부터 만드는 실제 시운전은 다시 하지 않았어요. B는 선택형 프로필로 두고 실제 원고 파일럿에서 재심 감소를 확인해야 해요.

### 2026-10-31 파일럿 v2와 후속 수정

같은 주제로 조정된 B를 다시 실행했어요(`logs/lab-upgrade-eval/b-pipeline-trial-v2`). 호출 24→15회, 1,611→1,321초로 예산 안에서 끝났지만 첫 원고 심사 65점·major, 부분 수정 1회 뒤 독립 재검증 revise로 보류됐어요. 조정 전의 75점은 한 번 고친 원고의 점수라 직접 비교하지 않아요. 원인과 수정은 아래와 같아요.

- 버전 번호 오판: `evidence.significant()`가 'LTS인 5.2'·'5.2 문서'·'6.1.2'를 통계로 잡아, 검증관의 지지 판정을 확인 불가로 내리고 편집장 지시에 '5.2를 쓰지 말라'는 상충 경고를 붙였어요. 점이 둘인 x.y.z와 버전 문맥(LTS·버전·문서·릴리스 등)의 x.y를 대조에서 빼요. 5.2%·45.64초 같은 통계는 그대로 대조해요.
- 코드 예제: 반복 결함이 문서로 검증할 수 없는 코드 문제(클래스 밖 테스트 메서드, assertNumQueries 기대값)였어요. `office/code_check.py`가 파싱 실패·클래스 밖 test 메서드를 자동 점검 지적으로 돌려요(항상). `OFFICE_CODE_RUN=1`이면 본문의 모델·테스트 블록을 임시 앱으로 묶어 별도 프로세스·메모리 SQLite에서 실행하고, 결과를 근거 묶음의 `[코드 실행 확인]` 블록으로 검증관·편집장에게 넘겨요. 실제 실패는 B 통합 심사의 필수 수정이 되고, 본문 밖 모델 참조(NameError)·URL·템플릿 같은 환경 차이는 '확인 못 함'으로만 표시해요. v2 초안의 '필자 예상값' assertNumQueries(2)는 실행하면 통과해요. 모델이 쓴 코드를 실행하므로 운영 서버에서는 기본으로 꺼 둬요(비밀값 환경변수 미전달, 프로젝트 경로 미포함, 90초 제한이지만 OS 수준 격리는 아니에요).
- 모델 배치: Astra 입력 약 105만 토큰 중 67%(약 71만)·530초가 집필 전 설계도 근거 수집이었어요. 수집(`purpose='gather'`)은 조사 모델 Sol medium이 맡고, 원고의 독립 검증(check·reverify·중재)은 Sol high가 해요(같은 날 Astra high에서 변경). 원문 문장 대조와 범위 계약은 모델과 무관하게 같아요. 실제 절감량은 다음 파일럿에서 측정해요.
- 회귀: office·common 526개 통과, Django check 통과. 비교용 실행은 `tmp/lab_upgrade_trial_v3.py select|atomic|data`(결과 `logs/lab-upgrade-eval/b-pipeline-trial-v3-<case>/`).

실제 실행의 기준선은 읽기 전용 `lab_quality_report --days 30 --output logs/lab-quality-baseline.json`으로 추출해요. 과거 실행에 호출 기록이 없으면 비용 0으로 해석하지 않아요. 모델 사용량·발행 가능 비율·사람 수정 시간을 같이 보고 B의 운영 선택을 결정해요.

운영 배포 전에는 운영 코드/데이터와 구독 계정의 모델·도구 가용성을 별도로 확인하고, 검증한 설정만 반영해요. 코드와 프로필 선택은 따로 되돌릴 수 있어요. `OFFICE_MODEL_PROFILE=a` 또는 `legacy`로 복귀해도 생성된 글·원장·체크포인트를 삭제하지 않아요.

## 3D A안

2026-10-31 최종 후속: B 배경과 연구원 8명의 고정 시점 이미지 합성 화면을 로컬에 적용하고 S3~S5 검증을 마쳤어요. 사용자의 다리 배치 피드백을 반영해 세 집필석은 인물·책상을 함께 생성한 배경으로 교체했어요. 아래 WebGL 기록은 이전 구현이며, 현재 기본 엔진은 `plate`예요. 상세는 [최종 그래픽 검증](lab-graphic-final-review.md), 프롬프트는 [그래픽 생성 기록](lab-graphic-credits.md)을 참고해요.

[디자인 계획](lab-3d-design.md)에 따라 실제 메시로 방·책상·자료실·회의 테이블·발행대와 8명을 모델링했어요. Three.js 0.187.0(MIT)을 자체 정적 파일로 고정하고 공식 npm 무결성 해시도 대조했어요. 기존 LimeZu 이미지의 3D 전환이나 재배포는 하지 않았어요. 미리보기 WebP는 구현한 장면을 렌더링한 33,940바이트 이미지예요.

- PC는 지연 로딩 후 장면을 표시해요. 모바일·동작 줄이기·데이터 절약 환경은 미리보기와 HTML을 먼저 보여주며, 버튼을 누르면 3D를 열어요.
- 실제 메시 클릭과 HTML 이름 버튼으로 연구원을 선택해 역할·최근 공개 활동을 읽어요. 실제 진행 상태는 유효한 공개 agent 키만 받아 별도로 표시해요. 대기 연출을 현재 작업으로 표시하지 않아요.
- 좌우 드래그·방향키·확대/축소·시점 초기화·움직임 정지를 제공해요. 저장된 최근 회의는 별도 패널에서 이전/다음 발언과 자동 넘김 정지로 탐색해요.
- 모바일 전용 `base_mobile.html`을 사용하고 공유 본문을 재사용해요. 모바일 메시를 합치고 세그먼트·그림자를 줄였어요. DPR 상한은 PC 1.5, 모바일 1.25이며 애니메이션은 최대 약 30fps로 제한해요.
- 장면이 화면 밖이거나 탭이 숨겨지면 GPU 루프·조회·재생을 멈춰요. WebGL 실패나 컨텍스트 손실은 정적 미리보기로 전환하며 이름 버튼과 활동 탐색을 유지해요.

Windows Chromium의 격리된 Playwright 세션과 임시 DB에서 1440px PC, iPhone UA·`force_version=mobile`·390px 모바일, reduced motion을 확인했어요. 실제 기기에서의 측정은 아니에요. 이름/메시 선택, 실제 진행 상태 형식의 테스트 응답, 회의 이전/다음/종료, 카메라 키보드, 정지 시 추가 렌더 0회, GPU 손실 시 미리보기, 가로 넘침 없음, 모바일 초기 3D 모듈 요청 없음과 선택 후 실행을 확인했어요. 페이지 JavaScript 오류는 없었어요. 실행 중인 상태와 회의 재생은 브라우저 응답을 대체한 명시적 테스트 데이터로 점검했고, 캡처한 최종 미리보기에는 그 데이터를 쓰지 않았어요.
